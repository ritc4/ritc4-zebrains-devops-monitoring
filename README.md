## 1. Архитектура и соответствие стеку ZeBrains
При проектировании решения я руководствовался не просто базовыми инструкциями, а стандартами Enterprise-разработки и стеком вакансии ZeBrains (Prometheus, Grafana, ИИ-ассистенты, автоматизация):

* **ОС и Веб-среда:** Ubuntu + Nginx. Защита периметра через межсетевой экран `UFW` (открыты строго порты 22 и 80).
* **Автоматизация 2026 (Next-Gen Cron):** Вместо устаревшего планировщика Vixie Cron развернута связка **Systemd Service + Systemd Timer**. Это обеспечивает лучшую изоляцию процессов, централизованное логирование в `journald` и контролируемые таймауты.
* **Инфраструктура самовосстановления (Self-Healing):** Для веб-сервера Nginx настроена декларативная политика автоматического перезапуска при сбоях средствами Systemd. Это разделяет зону ответственности между автоматическим исправлением инцидентов первого уровня и системой мониторинга.
* **DevSecOps (Управление секретами):** В коде Bash-скрипта полностью отсутствует хардкод токенов. Токен Telegram Bot API инжектируется через переменные окружения на уровне демона `systemd`.
* **Наблюдаемость (Observability-ready):** Скрипт не просто пишет лог, а генерирует метрики в формате `Prometheus TSDB` (`/var/log/nginx-checker/metrics.prom`), что позволяет бесшовно подключить Prometheus + Grafana из стека компании для визуализации доступности.

## 2. Основные команды настройки infrastructure

### Шаг 1: Развертывание Nginx и кастомизация страницы
```bash
sudo apt update && sudo apt install nginx -y
echo "<h1>ZeBrains Enterprise Stack</h1>" | sudo tee /var/www/html/index.html
sudo systemctl start nginx && sudo systemctl enable nginx
```

### Шаг 2: Настройка отказоустойчивости веб-сервера (Self-Healing)
Для автоматического поднятия Nginx в случае его аварийного завершения или зависания настраивается переопределение системного юнита через команду `sudo systemctl edit nginx`:
```ini
[Service]
Restart=on-failure
RestartSec=5s
```

### Шаг 3: Сетевая безопасность (Firewall)
Согласно ТЗ, извне доступны только протоколы SSH и HTTP:
```bash
sudo ufw default deny incoming
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw --force enable
```

### Шаг 4: Подготовка Telegram-инфраструктуры для алертинга
1. Через официального бота `@BotFather` инициировано создание нового бота с помощью команды `/newbot`. Получен токен доступа (`TELEGRAM_TOKEN`).
2. С помощью специализированного сервисного бота `@userinfobot` определен персональный цифровой идентификатор аккаунта (`CHAT_ID`) для отправки мгновенных PUSH-уведомлений о падении веб-сервера.

### Шаг 5: Изоляция прав доступа к логам
В соответствии с DevOps Best Practices, чтобы не запускать скрипты от root и избежать уязвимости полных прав `777` на системные каталоги, создана изолированная подпапка с передачей прав конкретному пользователю `ubuntu`:
```bash
sudo mkdir -p /var/log/nginx-checker
sudo chown -R ubuntu:ubuntu /var/log/nginx-checker
sudo chmod 750 /var/log/nginx-checker
```

### Шаг 6: Регистрация и активация автоматизации в Systemd
После размещения конфигурационных файлов юнитов в системной директории, выполняется перезагрузка конфигурации менеджера и запуск таймера на постоянной основе:
```bash
sudo systemctl daemon-reload
sudo systemctl enable --now nginx-checker.timer
# Проверка статуса и расписания активных таймеров в системе:
systemctl list-timers --all | grep nginx-checker
```

## 3. Отчёт по работе с ИИ (Claude / ChatGPT)

В соответствии с требованиями вакансии к "практическому опыту работы с ИИ", я использовал языковую модель как интерактивного напарника для парного программирования (Pair Programming).

### Где ИИ ускорил работу:
* Генерация синтаксиса получения чистого статус-кода ответа через `curl -w "%{http_code}"`.
* Подготовка базового шаблона конфигурации `Systemd-Timer`.

### Критический анализ: Где ИИ ошибся или дал неточный ответ
Нейросети склонны генерировать "наивный" изолированный код без учёта долгосрочной эксплуатации системы в реальном продакшене. В процессе ревью я выявил следующие критические дефекты и упущения в ответах ИИ:

1. **🚨 Грубая ошибка безопасности (Хардкод токенов):** ИИ предложил объявить переменные `TELEGRAM_TOKEN="..."` прямо внутри скрипта. Если бы я скопировал это "вслепую" и выложил в публичный репозиторий GitHub, секреты компании были бы мгновенно скомпрометированы. 
   * *Моё решение:* Я заставил ИИ переписать логику на чтение системного окружения, а секреты вынес в конфигурацию `Systemd Environment`.
2. **⏳ Риск бесконечного зависания сетевого запроса и ложных срабатываний:** Первичный скрипт от ИИ содержал конструкцию, которая при частичном зависании веб-сервера ждала бы ответа вечно, порождая лавинообразное накопление процессов. Кроме того, ИИ не заложил защиту от кратковременных сетевых колебаний (Network Flapping).
   * *Моё решение:* Внедрен строгий режим продакшена (`set -u -o pipefail`), флаги жесткого ограничения времени запроса (`--connect-timeout 3 --max-time 5`), а также **логика из 3 повторных попыток** с интервалом в 1 секунду (`--retry 3 --retry-delay 1`). Дополнительно на уровне Systemd-сервиса выставлен лимит `RuntimeMaxSec=15s` для гарантированного уничтожения «зависших» процессов.
3. **📂 Проблема "Legacy-подхода":** На запрос автоматизации ИИ по умолчанию выдал конфигурацию для старого `crontab`. В современной Cloud-Native инфраструктуре Cron считается устаревшим из-за отсутствия гибкого контроля зависимостей, изоляции и логирования.
   * *Моё решение:* Архитектура переведена на декларативные таймеры `systemd`.
4. **🔄 Игнорирование жизненного цикла данных и отказов самого мониторинга:** ИИ спроектировал бесконечную запись в текстовый файл без ротации (риск переполнения диска `DiskFull`). Также ИИ перенаправлял ответы Telegram API в `/dev/null`, из-за чего при падении самого Telegram сбой мониторинга остался бы незамеченным.
   * *Моё решение:* Самостоятельно спроектирован манифест для утилиты `logrotate` с глубиной хранения архивов в 1 месяц и сжатием в `.gz`. В коде скрипта реализована **обработка ошибок отправки алертов**: если API Telegram недоступен, резервная запись об инциденте принудительно отправляется в стандартный поток ошибок (`>&2`), который перехватывается системным журналом `systemd journald`.

## 4. Конфигурационные файлы проекта

### Итоговый Bash-скрипт (`check_nginx.sh`):
*(См. исходный код в файле check_nginx.sh в корне репозитория)*

### Юнит автоматизации (`/etc/systemd/system/nginx-checker.service`):
```ini
[Unit]
Description=Nginx Web Server Checker Service
After=network.target

[Service]
Type=oneshot
User=ubuntu
Environment="TELEGRAM_TOKEN=YOUR_BOT_TOKEN_HERE"
Environment="CHAT_ID=YOUR_CHAT_ID_HERE"
ExecStart=/home/ubuntu/check_nginx.sh
RuntimeMaxSec=15s
```

### Таймер автоматизации (`/etc/systemd/system/nginx-checker.timer`):
```ini
[Unit]
Description=Run Nginx Checker every minute

[Timer]
OnBootSec=1min
OnUnitActiveSec=1min
AccuracySec=1s

[Install]
WantedBy=timers.target
```

### Настройка ротации логов (`/etc/logrotate.d/nginx-checker`):
```text
/var/log/nginx-checker/*.log {
    weekly
    rotate 4
    compress
    delaycompress
    missingok
    notifempty
    create 0640 ubuntu ubuntu
}
```

## 5. Тестирование отказоустойчивости (Chaos Engineering)

Каждый сценарий поведения системы был детально проверен в изолированной среде разработки:

* **Тест №1: Штатный режим работы (Позитивный сценарий):** При стабильно запущенном Nginx таймер инициирует проверку каждую минуту. Скрипт фиксирует статус-код `200`, добавляет строчку `SUCCESS` в файл `check.log` и обновляет метрику в файле `metrics.prom` (`nginx_site_available 1`). Telegram-канал при этом остается чистым (алерты отсутствуют), не перегружая инженеров лишней информацией.
* **Тест №2: Падение сервиса (Негативный сценарий):** Имитировано падение веб-сервера через ручной останов процесса `sudo systemctl stop nginx`. Ближайший триггер таймера зафиксировал сетевой статус-код `000`, мгновенно отразил инцидент в логе со статусом `ERROR`, перевел экспортируемую для Prometheus метрику в состояние `0` и отправил структурированный PUSH-алерт в Telegram.
* **Тест №3: Зависание шлюза (Дроп пакетов):** Настроена временная блокировка трафика через команду `sudo iptables -A INPUT -p tcp --dport 80 -j DROP`. Благодаря внедренным таймаутам и логике повторов, сетевой запрос прервался ровно через заданные промежутки времени. Система не зависла, процессы не накопились, а благодаря директиве `RuntimeMaxSec=15s` юнит гарантированно завершил работу. Резервный алерт о недоступности успешно доставлен в Telegram.
